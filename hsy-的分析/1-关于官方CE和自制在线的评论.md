我的结论很明确：现阶段应以官方的“搜索 + 成功证明/反证回放 + CE”作为主线；在线 REINFORCE 可以保留做研究性对照，但不建议现在替代官方方案。

原因不是“CE 永远优于 RL”，而是当前在线实现还有几个关键问题：

1. “官方 CE 有模仿天花板，不能超过搜索”这个说法不准确。

官方不是模仿一个固定教师，而是循环执行：

当前网络 → 搜索得到更好的成功路径 → CE 蒸馏回网络 → 新网络再搜索

因此它完全可能超过上一代策略。AlphaProof 的主训练和 TTRL 用的都是这套 AlphaZero 式专家迭代。官方只把成功证明、成功反证中的路径送入 replay；失败搜索和 timeout 不训练 policy。所以不能简单概括成“CE 只是静态模仿，在线 RL 才能超越老师”。

2. “CE 有 token 级梯度，REINFORCE 只有一个梯度”也不严谨。

因为：

log π(a|s) = Σₜ log π(aₜ|s,a<ₜ)

所以 REINFORCE 同样会对动作中的每个 token 反传。真正的区别是：

- CE：每个 token 都有明确的正确标签；
- REINFORCE：所有 token 共用同一个序列奖励，无法判断究竟哪个 token 或哪一步造成成功/失败。

另外，NLL 并不是“有界损失”；它在正确 token 概率趋近于 0 时可以无限大。CE 通常更稳定，主要是因为监督目标明确、无需估计稀疏回报，而不是因为损失有界。

3. 当前的 βΔ² 不能算可靠的 KL 信赖域。

若样本刚由 π_old 采出，更新前 θ=θ_old，则 Δ=0，于是：

∇(βΔ²)=2βΔ∇logπ=0

也就是说，在最需要限制的第一次参数更新上，这个“KL 锚”实际上不起作用。等样本变旧、Δ≠0 后它才产生梯度，但此时 -rΔ 又没有 importance ratio 或 PPO clipping，已经是有偏的 off-policy 更新。它既不是精确 KL，也不是完整的 PPO/TRPO。

4. batch=50 并不会自动变成“小号专家迭代”。

当前代码里的 learn_batch_size 统计的是 Transition/event，不是独立问题。一条证明里的 50 个 event 高度相关，有效样本量远小于 50；而且无论 batch 多大，目标仍然是带序列奖励的 policy gradient，不会因为 batch 变大就变成搜索监督 CE。CE 的 batch size 同样会影响优化，官方的 4096 是规模设定，不能解释成“CE 对 batch 不敏感”。

5. “失败就给负奖励”未必是优势。

一条最终失败的轨迹中，前几步可能完全正确，只是后面选错了。把同一个负奖励施加给所有步骤，会把好动作也一起压低，这是典型的信用分配错误。除非有逐步 advantage、可靠 critic 或搜索反事实信息，否则负样本不一定比“只学习已验证成功路径”更可靠。

因此，如果现在必须二选一，我会选官方方式：

- 只训练 Lean 严格验证过的证明与反证路径；
- policy 使用逐 token CE；
- value 学剩余步数的 64 桶目标；
- 保留 SFT 混合，防止策略漂移；
- 本机可以使用较小 batch 和梯度累积，不必机械复刻 4096；
- 在线搜索继续产生新数据，但参数更新仍先采用 CE 蒸馏。

在线方案可以作为后续消融实验，但至少应先补上：按独立问题组 batch、advantage/bas线、importance ratio 或 PPO clipping、真正可测的 KL、优化器状态回滚，以及更新前后的固定验证集验收。

一句话总结：官方方案不是“保守模仿”，而是“搜索负责改进，CE 负责稳定蒸馏”。就目前代码成熟度和证据而言，它明显比这个简化的 REINFORCE+Δ² 更适合作为主线。****
